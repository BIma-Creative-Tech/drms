## Phase B-2 (web + server) — implemented 2026-10-11

- **D1** label "Pengajuan Baru" (`REQUEST_TYPE_LABELS.advance`), value `advance` unchanged.
- **D3** lines: total = qty × harga satuan (qty empty = 1, half-up to whole Rupiah) computed in the collection hook
  (`normalizeLines`, every write path: admin form, `/api/v1`, sync) and enforced by `pk_expense_frozen_check` while the
  request is editable; `receiptAmount` ("Nominal sesuai nota") per line → flag kind `receipt_amount_mismatch` ("Selisih
  nota", info ≤ rounding tolerance, else warning) recomputed on every line edit, submit and receipt resubmit.
  Legacy rows: editable lines got `unit_price = total ÷ qty` when exact (else stay without unit price and must be
  completed before submit); locked requests untouched (content hash unchanged).
- **Item 3** read-only "Rincian pengajuan" summary on locked requests (header inputs only while editable).
- **Point 13** LPJ photos (`settlements.photos`, media-receipts, max 10), editable at LPJ Draft / Revisi, frozen at submit.
- **PB numbering** (owner 2026-10-11): monthly from 1 per PT, `PB/<shortCode>/<YYMM>/0001`.

## Phase C (server + web) — implemented 2026-10-11

- **D4 RAP mandatory / realisation:** every expense line names a RAP item of the request's project
  (`expense_requests_lines.rap_item_id`). Submit: required on every line when the project has ≥ 1 active RAP item; a
  **konstruksi** project without RAP cannot send requests ("Project konstruksi ini belum punya RAP"). RAP exists for
  konstruksi only (P3) → other project kinds without RAP stay unconstrained (open question below). *Superseded
  2026-10-11: every project with a RAB — see "D4 amendment".* Per item: planned =
  round(volume × harga satuan); realised = Σ line totals of requests from the final approval onward (`BUDGET_COMMITTED`);
  transferred (Ditransfer and later) and verified (valid receipts after LPJ / receipt verification) also shown; remaining,
  percent. Over plan → flag `rap_over_budget` "Melebihi RAP" (warning, never blocking) raised at submit / line edit,
  refreshed before every decision and, after a final approval, on the project's other pending requests; live
  `lines[].rapOverBudget` in the detail. Flag + live state only for Direktur / Admin / Finance / PM (Staff never sees RAP
  values, owner 2026-10-10); the flag text carries no amounts.
- **D2 no non-project requests:** project required to submit; `costCenterId` from the requester is ignored (field not
  writable, old APKs keep working). Finance sets the cost center when recording the transfer (`transfers.cost_center_id`,
  mandatory; default = the new `projects.cost_center_id`); the transfer KK (and the LPJ refund KM / shortfall KK) carry the
  project AND that cost center → K-15 "Pusat biaya" (dashboard card, report filter `pusat`) follows Finance's choice.
  Approval routing uses the project PM only (a request always has a project now). Legacy cost-center requests stay valid:
  readable, their workflow continues; a legacy DRAFT that gets a project drops its cost center; a legacy request withdrawn
  after a submit may be sent again as it was.
- **DB (20261012_400000 / 400100):** content hash includes `rap_item_id` only when set (existing hashes unchanged); line RAP
  item must belong to the request's project; new requests have no cost center, a stored one only goes away, Draft → sent
  needs a project (legacy exception); advance / reimburse transfers need a cost center of their PT; manual cash entries stay
  "project OR cost center", request-flow entries may carry both.
- **Web:** project detail tabs **Proyek / RAP / Pengajuan** (D8 search, filters, pages; RAP items as cards ≤ 640 px);
  "Item RAP" picker in the line dialog (+ "RAP …" under the line, "Melebihi RAP" chip); Direktur dashboard card
  **Monitoring RAP**; transfer form **Pusat biaya** (pre-selected project default); request sidebar no longer repeats the
  header (Nomor, Status, Dibuat oleh, Grand total, Tanggal …; "Aturan approval" Finance / Admin only; "Alasan perubahan"
  only in Revisi Nota); Verifikasi LPJ receipts as cards ≤ 640 px.

## D4 amendment — RAP for every project with a RAB (owner 2026-10-11) — implemented

Owner: "RAP wajib untuk semua proyek yang punya RAB" (not only konstruksi); "Melebihi RAP" stays warning-only. ADR 0020
amendment 2026-10-11. Branch `feat/d1010-f-rap-all`.

- **Rule:** a project of any kind with RAB > 0 (and every konstruksi project) needs ≥ 1 active RAP item before a request
  can be submitted → 400 `projectId` **"Project belum punya RAP — hubungi PM"** (server = web = APK text). Drafts save;
  submitted requests stay valid; a project without RAB and without RAP is not constrained.
- **RAP for every kind:** web project tab **RAP** = items + plan vs realisation + **Kelola RAP** (Excel import / export,
  "Pakai template" on an empty RAP, "Simpan sebagai template") for the project PM and Direktur/Admin. Outside konstruksi:
  tahapan optional (existing stage only; an import never creates one), the RAP never drives the stage progress, no
  daily-report quantities (ADR 0020 §1 unchanged). Konstruksi keeps its Laporan harian RAP page.
- **Templates per project kind** (`projectKind`, empty = any kind; existing templates → konstruksi).
- **Nudges:** PM dashboard "Project Anda belum punya RAP" (team projects), Direktur dashboard "Project ber-RAB belum
  punya RAP" (every readable project); web request form banner + line dialog; APK draft editor card, line editor helper,
  project RAP tab card.
- **Existing data / go-live:** no automatic RAP. Migration `20261013_400100_d1010_rap_all_guard` logs the projects with a
  RAB and no RAP; the go-live import warns per imported project with a RAB (the import file has no RAP sheet — PMs fill
  the RAP on the RAP tab after the import).
